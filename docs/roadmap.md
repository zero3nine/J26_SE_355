# Implementation roadmap

Use this order to make the research pipeline recoverable, keep repeated imports from distorting the sample, and produce one reproducible SkillScope publication. Each step can be reviewed on its own. The [issue register](suggestions.md#current-issues) records evidence and open questions.

| Order | Work | Done when |
| --- | --- | --- |
| 1 | **Reopen saved batches.** Start with one saved raw batch, then add its cleaned output. Let the user pick a batch by ID and show its stage and row count. Handle live and historical batches explicitly. | A completed batch can be reopened after a browser refresh and a server restart. The user can continue to cleaning or master import without collecting again. A missing or partial artifact produces a clear message. For appended batches, reopening reproduces the intended record set with its source batch IDs. |
| 2 | **Make master imports safe to repeat.** First cover exact re-imports and metadata-only corrections. Then add portal-specific URL identity rules with collision review. Treat a repeat observation, an update to the same posting, and a potential repost as different cases. | Replaying an identical batch adds zero jobs and zero content versions, while the import audit records the attempt. A salary, work-mode, or classification correction survives a re-import. Approved aliases resolve to one job without merging distinct adverts. A failed row leaves neither a partial job update nor a version. |
| 3 | **Establish supported collection paths.** Repair the OCR test import and cover single-vacancy listing discovery in offline tests. Review the browser toggle and browser/image safeguards before a permitted live pilot. Start with ITPro and Shine. Add an OCR case for TopJobs and check TimesJobs, XpressJobs, and pending portals individually. Steps 1–2 can use historical files while this work runs. | A single-vacancy listing yields its job. A source matrix records listing and detail results, required browser/OCR setup, date and description coverage, and failure categories. Fixture results and dated live observations are recorded separately. Restricted sources produce an explicit restriction result. Windows setup and focused regressions work in a clean environment. |
| 4 | **Save one matched extraction run reliably.** Capture the input job set, actual threshold, model and taxonomy versions, and outcomes for both methods. First make the save atomic or safely resumable. Then let users reopen the saved run and inspect zero-skill results and failures. | Retrying an interrupted save cannot make a partial run available to readers. A small fixture with a matched result, a successful zero-skill result, and a failure shows three distinct outcomes. A later threshold experiment leaves the first run unchanged. |
| 5 | **Make research results comparable.** Fix the temporal low-sample period first. Then align cohort and extraction-run selection across role, relationship, regional, and temporal analysis wherever they report the same measure. Validate richer trend and forecast claims only after calendar and cohort handling is stable. | A hand-calculated fixture preserves true zeros and excludes low-sample months. Shared measures agree on the eligible job count, conditional measures show their denominator, and lexical/semantic comparisons use the same jobs and calendar. Any forecast presented as validated has evaluation for its displayed horizon and configuration. |
| 6 | **Publish one reviewed empirical sample.** Review source coverage, benchmark evidence, exclusions, and disclosure limits before exporting a matched cohort. Verify the separate public runtime with the sanitized snapshot. | A teammate can reproduce the publication from recorded inputs. The dashboard and CSVs report provenance and sample scope. The deployed runtime serves the snapshot read-only and passes health and export checks. |

The first implementation slice is reopening one saved raw batch. Use a small historical CSV to prove refresh and restart recovery on Windows. It gives the team a way to resume work without depending on live scraper availability or a database migration.
